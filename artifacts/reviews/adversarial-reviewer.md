# Adversarial Review Findings

## 1) High — Forged consumer artifact bundles can pass `check --repo-root` without any execution provenance
- Evidence:
  - `checkCommand` validates consumer roots in observed-latest mode and skips runtime-evidence checks for non-default roots ([src/commands/validation.js:134](/Users/jamiecraik/dev/evals/src/commands/validation.js:134), [src/commands/validation.js:143](/Users/jamiecraik/dev/evals/src/commands/validation.js:143), [src/commands/validation.js:168](/Users/jamiecraik/dev/evals/src/commands/validation.js:168)).
  - `resolveRepoRootOption` accepts any existing directory as a trusted root ([src/lib/repo-root-option.js:17](/Users/jamiecraik/dev/evals/src/lib/repo-root-option.js:17)).
  - Latest validation is structural/hash consistency over files under that root, not provenance of who/what produced them ([src/lib/latest-run.js:113](/Users/jamiecraik/dev/evals/src/lib/latest-run.js:113), [src/lib/latest-run.js:145](/Users/jamiecraik/dev/evals/src/lib/latest-run.js:145)).
- Failure scenario (constructed):
  1. A consumer repo (or attacker in CI workspace) writes a hand-crafted `.harness/evals/runs/latest.json` and matching artifact files.
  2. Hashes in `manifest.json` are computed correctly for those fabricated files.
  3. `pnpm evals check --repo-root <consumer>` runs in observed-latest mode, omits runtime-evidence validation, and returns `passed`.
  4. Downstream automation treats this as readiness, even though no trustworthy eval execution occurred.
- Why this matters: This creates a fake-readiness path exactly where contract verification is expected to gate delivery.
- Practical validation:
  - In a temp repo root, manually create a minimal self-consistent latest/result/manifest/scorer/baseline/trace set and run `pnpm evals check --repo-root <temp> --json`. Confirm pass without invoking `pnpm evals run` in that root.

## 2) Medium — Promotion authority is declared but never enforced, enabling “green without promotion” drift
- Evidence:
  - Baseline output hardcodes `promotion_status: "not_requested"` regardless of fixture promotion intent ([src/commands/run.js:134](/Users/jamiecraik/dev/evals/src/commands/run.js:134)).
  - Baseline scorer checks only presence/comparison; it ignores promotion semantics ([src/lib/scoring.js:112](/Users/jamiecraik/dev/evals/src/lib/scoring.js:112)).
  - Case contract requires `promotion.status` and `promotion.baseline_owner`, but run logic does not enforce/interpret `promotion.status` ([src/lib/case-contract.js:40](/Users/jamiecraik/dev/evals/src/lib/case-contract.js:40)).
- Failure scenario (constructed):
  1. A suite encodes a case with promotion intent (`promotion.status` indicates non-default governance expectations).
  2. Runner always emits `promotion_status: not_requested` in `baseline-result.json`.
  3. Scorers still pass if baseline presence expectations match.
  4. Aggregated run/suite returns pass, falsely implying promotion-safe readiness while promotion gate was never actually exercised.
- Why this matters: It allows policy documentation to claim promotion-aware contracts while runtime behavior cannot fail on promotion drift.
- Practical validation:
  - Create a case with non-default `promotion.status` and baseline expectations that otherwise pass; run and inspect `baseline-result.json` plus verdict. Confirm verdict can pass with `promotion_status` unchanged.

## 3) Medium — Synthetic output and required-output scorer are coupled, allowing self-fulfilling success signals
- Evidence:
  - Runtime execution is always synthetic in phase-one run path ([src/commands/run.js:182](/Users/jamiecraik/dev/evals/src/commands/run.js:182)).
  - Synthetic stdout is generated by fixed helper text ([src/lib/scoring.js:18](/Users/jamiecraik/dev/evals/src/lib/scoring.js:18)).
  - Required-output scorer checks substring containment against that same generated stdout ([src/lib/scoring.js:55](/Users/jamiecraik/dev/evals/src/lib/scoring.js:55), [src/lib/scoring.js:68](/Users/jamiecraik/dev/evals/src/lib/scoring.js:68)).
- Failure scenario (constructed):
  1. Contract authors depend on `required-output` as a readiness signal.
  2. The run path never executes project behavior; it emits canned synthetic lines.
  3. `required-output` passes because needles are matched against canned output.
  4. Teams interpret pass as behavior evidence, but signal only proves internal formatter consistency.
- Why this matters: It blurs “contract verifier vs behavior oracle” boundaries and can produce misleading green signals in program-level reporting.
- Practical validation:
  - Modify a fixture’s `expected.required_output_contains` to existing canned substrings and rerun; compare pass outcome against the fact no external command was executed.

## 4) Low — Multi-case suite runs overwrite one shared latest pointer, creating context-flip readiness confusion
- Evidence:
  - `runSuite` executes cases sequentially and each `executeCase` writes `latest.json` under the same artifact root ([src/commands/run.js:401](/Users/jamiecraik/dev/evals/src/commands/run.js:401), [src/commands/run.js:343](/Users/jamiecraik/dev/evals/src/commands/run.js:343)).
  - Suite summary is returned, but there is no suite-scoped immutable pointer for all case outputs ([src/commands/run.js:411](/Users/jamiecraik/dev/evals/src/commands/run.js:411)).
- Failure scenario (constructed):
  1. A suite with multiple cases is run; earlier case validates one contract, later case validates another.
  2. Last case rewrites `latest.json`.
  3. Operator runs `pnpm evals state --json` or non-smoke `check` and sees only last-case context.
  4. If humans or automation assume “latest == suite outcome,” they can make decisions on the wrong case context.
- Why this matters: This is a composition bug between suite aggregation and single-pointer state reporting.
- Practical validation:
  - Run a two-case suite with intentionally different `case_id`/expected contexts, then inspect `latest.json` and `state`; verify only last case remains addressable by latest pointer.

## Residual Risks
- Consumer workflows may institutionalize `observed-latest` pass as deployment authority without provenance requirements.
- Documentation-level claims about promotion governance can outpace executable enforcement, causing silent drift.

## Testing Gaps
- No adversarial fixture test that asserts `check --repo-root` fails on unsigned/non-provenance artifacts.
- No test asserting promotion semantics affect pass/fail when `promotion.status` is non-default.
- No suite-level test asserting multi-case pointer semantics (e.g., explicit suite summary pointer vs mutable latest).
